## 1. 目标和判断标准

本方案参考 AlphaStar、IMPALA、R2D2、MAPPO 和 DI-engine 的公开设计，目标不是把项目直接改成某一个论文系统，而是在保留现有 PPO/FPO/PolicyFlow 对照资格的前提下，逐步增加以下能力：

1. 采样和学习解耦，能够观察并控制 Actor 与 Learner 的策略版本延迟。
2. 对当前观测之外的短期历史建模，减少部分可观测和延迟奖励造成的决策抖动。
3. 让动作表示匹配 Dino 的真实语义，逐步从 4 维连续阈值动作迁移到可解释的混合动作。
4. 为成功轨迹、行为克隆、离线数据和对手快照建立独立的数据协议。
5. 在真正引入多智能体和自博弈前，先有可重复的固定对手评估、消融实验和失败熔断。

改进是否有效，统一使用以下指标判断：environment steps、wall-clock time、steps/s、单次推理延迟、GPU 显存、平均回报、自然终止胜率、最终食物、非法部署率、超时率、truncated 率和至少 3 个随机种子的方差。任何新方法都必须与当前结构化 PPO 基线使用相同 Unity 构建、协议、地图种子和评估局数。

## 2. 当前训练系统已经具备的能力

当前项目不是“只有一个 PPO 脚本”，已有不少接近前沿训练工程的基础设施：

| 当前能力 | 代码位置 | 现状判断 |

| 策略版本隔离 | flow_rl/src/flow_rl/training/versioned_collector.py、dino_parallel_ppo.py | 一个 rollout 只接收一个 policy_version，更新成功后才进入下一版本，当前属于严格 on-policy PPO。 |
| 推理微批 | flow_rl/src/flow_rl/training/dino_batched_policy.py | 已有同步环境轮次和微批推理，能减少 GPU 小批量调用开销。 |
| GAE 和终止语义 | flow_rl/src/flow_rl/data/gae.py | 已区分 terminated 与 truncated，自然终止不 bootstrap，时间限制/中断按项目契约处理。 |
| 集合编码器 | flow_rl/src/flow_rl/models/dino_set_transformer.py | 已使用 valid mask、ISAB/SAB、区域交叉注意力和全局时间特征，明显优于直接展平全部实体的 MLP。 |

因此，本项目第一步不应重复实现“并行环境、Set Transformer、版本化采集和 checkpoint”。更合适的顺序是先补齐监控和实验契约，再有选择地增加记忆、混合动作和 Actor-Learner。

## 3. 主要差距

### 3.1 当前是严格版本隔离的同步更新，不是可观测的异步 Actor-Learner

当前 VersionedCollector 在 rollout 内拒绝混合策略版本。这对 PPO 的正确性很有价值，但它也意味着：

~~~text
收集一个完整 rollout
→ 停止接受这一版本的数据
→ Learner 更新
→ 进入下一个版本
~~~

AsyncUnityVectorEnv 的异步主要是 Unity step 的并发，不代表多个独立 Actor 持续向 Learner 推送旧策略数据。项目目前没有显式的策略广播、队列年龄、Actor lag 或 stale-sample 监控，也不应把当前实现称为 IMPALA。

### 3.2 观测是结构化的，但策略没有短期记忆

Set Transformer 处理了当前时刻的墙、守军、房屋和恐龙集合，却没有显式保存上一决策的隐藏状态。对于“刚才等待过什么”“敌方防御是否刚被摧毁”“早期动作是否造成后续资源变化”等信息，模型只能依赖当前观测中的残留信号。

### 3.3 当前动作协议仍是 4 维连续阈值编码

dino_attack_structured_set_v2 的动作是：

~~~text
zone ∈ [-1, 1]
u    ∈ [-1, 1]
v    ∈ [-1, 1]
choice ∈ [-1, 1]
~~~

再由 dino_protocol.py 按阈值解码为区域、区域内坐标、等待或恐龙种类。当前 TanhGaussianActor 对 4 个维度建立独立高斯分布，这个设计适合保持现有基线和导出兼容性，但没有显式表达：

~~~text
先选择 Wait / 兵种
→ 再选择区域
→ 只有需要部署时才选择坐标
~~~

因此，非法或无意义组合要靠 Unity 侧拒绝和惩罚来学习。

### 3.4 没有可以安全混入 PPO 的经验回放和离线数据协议

当前 PPO batch 保存 old_log_probs，这是 on-policy 更新的正确做法。不能把任意旧 checkpoint、失败轨迹或行为克隆数据直接塞入 PPO batch，否则会破坏概率比和优势估计的语义。离线数据需要独立的数据集版本、来源、动作协议和算法入口。

### 3.5 没有对手人口和多智能体训练需求

当前主要是一个全局进攻决策 Agent，防御侧由游戏规则和固定单位行为执行。AlphaStar 式 League、MAPPO 集中式 Critic 只有在引入可学习防守方、队友或不同难度对手之后才有实际意义。现在直接增加 League 会增加复杂度，却无法证明收益。

## 4. 推荐目标架构

建议把训练系统分成五个可替换层：

~~~text
Unity Actor 环境层
    ↓ 观测、奖励、终止、动作协议
采样层
    ↓ AgentIdentity、episode、policy_version、行为策略信息
策略服务层
    ↓ 编码器、记忆、动作头、Critic
学习层
    ↓ PPO / V-trace / MAPPO / BC 等独立更新器
评估与治理层
    ↓ 固定对手、快照池、指标、熔断、checkpoint
~~~

其中，现有 flow_rl 的环境适配、GAE、协议校验、日志和 checkpoint 继续作为共享基础设施；算法特有的 loss、概率模型、hidden state 和 replay 不能混入 Unity 适配层。

## 5. 分阶段实施方案

### Phase 0：基线和训练治理加固

**目标：先让后续改进可以被公平验证。**

保留当前 dino_attack_structured_set_v2、4D Gaussian PPO、Set Transformer 和严格版本隔离，新增以下能力：

1. 在 PPOUpdater 中加入可配置的 target_kl 和 update early-stop：当近似 KL 连续超过阈值时停止当前 epoch，并记录实际 epoch 数。
2. 记录 advantage_mean/std、value explained variance、ratio p01/p50/p99、KL、clip fraction、梯度范数、每个地图的非法部署率和资源拒绝率。
3. 为训练 run 生成不可变的 effective_config.yaml、协议 hash、Player hash、git 状态摘要和评估配置。
4. 将“在线 rollout 指标”和“冻结 checkpoint 评估指标”分成两个命名空间，避免把跨版本的在线回报误认为当前 checkpoint 的胜率。
5. 增加定期评估：每个 checkpoint 在固定地图种子上运行 deterministic 和 stochastic 两套评估，并保留失败轨迹。
6. 增加自动熔断：非有限 loss、KL 超阈值、成功率突降、truncated 激增、Unity 错误预算超限时保存诊断并停止，而不是继续生成一个不可用的 final checkpoint。

**退出标准：** 当前 PPO baseline 在 3 个 seed 上能重现；每次 run 都有完整配置和固定评估报告；现有协议和 checkpoint 兼容测试不回归。

### Phase 1：在不改变 v2 协议的情况下加入短期记忆

**目标：先验证记忆是否帮助当前任务，不改变动作接口。**

设计：

~~~text
SetTransformerDinoEncoder(o_t) → z_t
[z_t, h_{t-1}] → GRU/LSTM → h_t
h_t → Actor / Critic
~~~

具体改造：

1. 新增 RecurrentStateEncoder 或策略包装器，不修改现有 SetTransformerDinoEncoder。
2. 以 environment_id、process_generation、agent_id、episode_index 作为 hidden-state 键；重启、自然终止和 truncated 时清空对应状态。
3. VersionedActionInfo 和 transition 增加可选的 sequence_id、is_sequence_start，collector 按完整序列或固定长度切片，而不是把含有 hidden state 依赖的样本完全随机打散。
4. 对 padding sequence 使用 mask；GAE 仍以 episode 边界为准，不能让 hidden state 跨局泄漏。
5. checkpoint 保存网络参数和训练 RNG；hidden state 不跨重启恢复，恢复训练时从 episode 边界重新初始化。

先比较：

~~~text
A：当前 MLP/Set Transformer + Gaussian PPO
B：同样协议 + GRU(128) + Gaussian PPO
C：同样协议 + LSTM(128) + Gaussian PPO
~~~

**退出标准：** B/C 至少在固定种子和相同 environment steps 下没有降低稳定性；能够通过 Agent ID 重排、终止清空、截断 bootstrap 和 resume 边界测试。若无收益，保留当前无记忆基线。

### Phase 2：把连续阈值动作扩展为混合动作 v3

**目标：让动作概率结构匹配游戏语义，同时保持 v2 checkpoint 可复现。**

不得直接改变 dino_attack_structured_set_v2，应新建协议，例如：

~~~text
dino_attack_structured_hybrid_v3
~~~

推荐动作因子化：

~~~text
choice_head：Wait / Velociraptor / Pachy / T-Rex
    ↓ 只有 choice != Wait 时
zone_head：Z1 / Z2 / Z3 / Z4 / Z5
    ↓
coordinate_head：u, v 的连续分布
~~~

联合概率为：

$$
\log \pi(a|s)
=
\log \pi(c|s)
+\mathbf{1}[c\neq \text{Wait}]\log \pi(z|s,c)
+\mathbf{1}[c\neq \text{Wait}]\log \pi(u,v|s,c,z)
$$

实现要点：

1. 在 models/ 新增 DinoHybridActorCritic，不要修改现有 GaussianActorCritic 的参数形状。
2. categorical head 使用合法动作 mask；坐标 head 只在需要部署时计算，Wait 时不参与 log-prob 和 entropy。
3. 区域选择可以先使用 5 类 categorical；坐标仍使用 tanh Gaussian，减少一次性改动。
4. PPOBatch 增加动作组件、组件 mask 和联合 old_log_prob；PPO 仍对联合动作概率做 clip。
5. 新建 v3 codec、Unity C# 适配和 ONNX 输入输出签名；v2 的模型和构建继续可运行。
6. 先实现 v3 = v2 的等价映射测试，再比较独立 categorical/continuous head 的收益。

**不要在这一阶段加入 action chunking。** 当前计划已把多步动作归入阶段 9；应先完成单步 v3 的概率、终止和导出验证。

**退出标准：** v3 在固定观测上能正确完成 Python、ONNX、Unity 三端动作解码；Wait 不再生成无意义坐标；v2 基线的输出和 checkpoint 不受影响；至少完成 v2/v3 的同环境 steps 对照。

### Phase 3：Actor-Learner Lite 和策略延迟可观测性

**目标：先改造系统边界，再决定是否采用 V-trace。**

当前 ThreadPoolExecutor 只解决并行 step。建议新增一个轻量的进程/队列层：

~~~text
Actor 进程：Unity Player + 本地 adapter + 当前策略快照
        ↓ trajectory queue
Learner 进程：GPU policy + PPO updater
        ↓ policy broadcast queue
Actor 进程更新快照
~~~

每条 fragment 必须携带：

~~~text
actor_id
environment_id
process_generation
episode_id
policy_version_used
policy_version_received
created_at / received_at
old_log_prob 或行为策略摘要
~~~

第一版仍使用 PPO 的严格新鲜数据，只做：

1. 采样队列有界化；
2. 明确 policy broadcast；
3. 统计 queue depth、fragment age、policy lag、丢弃率和每个 Actor 的吞吐；
4. 只在 policy_lag == 0 或低于配置阈值时接受 PPO batch。

第二版再增加 IMPALA/V-trace 分支：

~~~text
μ = Actor 产生数据时的行为策略
π = Learner 当前策略
ρ_t = π(a_t|s_t) / μ(a_t|s_t)
~~~

V-trace/异步 off-policy 更新不能与现有严格 on-policy updater 混在一个函数中。应新增 VTraceUpdater、独立配置和独立指标，保留 PPO 作为可复现对照。若队列延迟很小，V-trace 可能只增加复杂度而不带来收益。

**退出标准：** Actor lag 可观测；故意延迟模型广播时，测试能复现并报告旧策略数据；PPO 严格模式和 V-trace 模式不会混淆；进程退出、Unity 重启和 checkpoint 边界安全。

### Phase 4：离线数据、行为克隆和受控回放

**目标：提高冷启动和稀疏奖励场景的样本效率。**

建立独立 DatasetManifest，每条轨迹记录：

~~~text
protocol_version
build_sha256
observation/action codec hash
source: human / PPO / scripted / evaluation
policy_version
map / seed / episode id
terminated / truncated
~~~

数据分三类：

1. **BC 数据：** 成功 PPO 轨迹或人工轨迹，用于 Actor 预训练。
2. **评估数据：** 只读，不能混入训练集。
3. **离线 RL 数据：** 包含失败和成功轨迹，供独立的 CQL/IQL/AWAC 等算法实验。

行为克隆只初始化策略，不修改 PPO 的 on-policy 语义。对现有项目，先复用已经存在的 Flow BC 管线，再考虑为 Gaussian PPO 增加 BC warm-start；不要直接把旧 checkpoint 的 transition 追加到当前 PPO rollout。

**退出标准：** 训练/验证按整局划分；数据清单能阻止不同协议、不同 Unity build 或旧动作 codec 混合；BC warm-start 与随机初始化的比较使用相同 environment steps 和相同评估种子。

### Phase 5：冻结对手、人口和多智能体扩展

**目标：只有在任务真正需要可学习对手或队友时，才引入 AlphaStar/MAPPO 风格机制。**

建议顺序：

1. 先冻结现有进攻策略作为防守评估对手。
2. 新增一个可学习防守 Agent 或可学习队友，使用独立的 observation/action protocol。
3. 先做 parameter sharing + centralized critic 的 MAPPO 对照。
4. 再加入历史 checkpoint 池、Elo/TrueSkill、固定比例的历史对手和针对性对手。
5. 最后才考虑 PFSP/League Training；每次新增策略必须保留旧策略，防止只针对当前对手过拟合。

不能把当前单 Agent 全局部署任务直接宣传为 MAPPO。没有队友、敌方学习者和联合状态时，集中式 Critic 只会增加接口和验证成本。

**退出标准：** 报告当前对手、历史对手和未见布局三种评估；记录 exploitability/对手覆盖，而不是只报告对当前快照的胜率；每个 Agent 的 credit assignment 和终止语义有测试。

## 7. 测试和验收矩阵

每个新增组件至少补以下测试：

| 范围 | 必须验证 |
|---|---|
| 动作 head | categorical/continuous shape、联合 log-prob、Wait mask、非法动作 mask、边界值 |
| 记忆 | batch 内 Agent ID 重排、episode reset、terminated/truncated、padding mask、固定 seed |
| Actor-Learner | policy broadcast 顺序、旧策略版本标记、队列上限、超时、丢弃和恢复 |
| V-trace | rho=1 时与无修正目标一致；大 lag 时权重截断；非有限值拒绝 |
| 回放/数据集 | manifest hash、协议和 build hash、整局切分、评估数据隔离 |
| checkpoint | v2/v3/recurrent schema 拒绝误加载；optimizer、RNG、normalizer 和构建 hash 恢复 |
| Unity 集成 | DecisionSteps 顺序、Agent ID 映射、自然终止/中断、动作 codec、Python/ONNX/Unity 输出一致 |

推荐的最小消融矩阵：

~~~text
A  当前 v2 Gaussian PPO
B  A + target-KL early stop
C  A + GRU
D  A + hybrid v3
E  A + Actor-Learner Lite（严格 on-policy）
F  E + V-trace
~~~

每个实验至少使用 3 个 seed；先比较 environment steps，再单独比较 wall-clock 和吞吐。不同动作协议、不同奖励或不同 Unity build 的结果不能放在同一张“算法优劣”曲线里。

## 8. 风险、取舍和明确不做的事

| 风险 | 控制办法 |
|---|---|
| 混合动作与旧 4D checkpoint 不兼容 | 新协议、新 policy 类、新 checkpoint schema；保留 v2 只读基线。 |
| GRU hidden state 串局 | 以完整 AgentIdentity 清理；重启和两种终止都测试。 |
| 异步队列导致 PPO 数据过时 | 第一版只记录 lag；V-trace 单独实现，不能偷偷把旧数据放进 PPO。 |
| 奖励塑形造成房屋/资源投机 | 保留正式奖励作为主指标，辅助奖励单独记录并做 reward ablation。 |
| League 只学会针对单个对手 | 固定对手、历史快照、未见布局分开评估。 |
| 训练吞吐提高但学习效果下降 | 同时报告 steps/s、wall-clock、回报和胜率，不能只看速度。 |
| 过早引入 action chunk | 遵守阶段 9 依赖，先完成单步动作和 v3 协议等价测试。 |
| 破坏当前阶段 8 验收 | 本方案先作为文档；实现时不改现有场景、ProjectSettings、Packages 和冻结模型。 |

本方案明确不做：

- 不把当前 ThreadPoolExecutor 称为完整 IMPALA/AlphaStar 系统。
- 不把 V-trace、Replay、League 和 MAPPO 一次性混入现有 PPO。
- 不用旧 v2 checkpoint 直接加载 hybrid、recurrent 或 action-chunk policy。
- 不通过增加奖励项来替代动作协议和评估问题。
- 不在没有固定对手和多智能体需求时引入 League。

## 9. 推荐执行顺序

~~~text
1. Phase 0：治理、KL 熔断、评估和诊断
2. Phase 1：GRU/LSTM 记忆，保持 v2 动作协议
3. Phase 2：hybrid v3 单步动作，保留 v2 对照
4. Phase 3：Actor-Learner Lite 和 policy lag 监控
5. Phase 4：BC / 离线数据 / 受控回放
6. Phase 5：按真实玩法需求引入 MAPPO、快照池和 League
7. 阶段 9：在单步契约稳定后再做 action chunking
~~~

第一项实际开发建议是 **Phase 0 的 target-KL early stop + 冻结评估报告 + policy lag/版本诊断字段**。这些改动不改变 v2 动作、奖励和 checkpoint 语义，能先解决当前“训练曲线、在线 episode 指标和部署模型是否可比”的问题，再为后续所有前沿方法提供可靠基线。
